# 02 玩法接入与关卡

这款游戏的玩法由哪些文件组成、要遵守的接口、关卡怎么生成、关卡节奏、难度怎么定义和量。规则本身在 `docs/01` 第 1 节。

> **现状（2026-11-22）**：规则骨架沿用上一版原型，代码里的名字还没改：`core/dig/` 里的 car = 小队方块，track = 排队区的一列，slot = 上场位，`dig` 事件 = 搬豆（`docs/01` 写作 `carry`），`depart` 事件 = 小队离场（`leave`）。已经做了：密排的拼豆画、方块和上场位、小人搬运、火车、技能加位 / 调队 / 磁铁、复活、试玩用的两关。还没做：连体块、问号块、锁和钥匙、云朵（方案待确认，`docs/01` 第 1.7 节；确认后换掉叠层画）、「想清楚」机器人、画的四个量、加速时间、前 50 关。剩下的事列在 `docs/07`。底座升级的那部分代码（`levels.json` 的 `pace`、`level-verify` 报时长）还没并进来。

## 1. 玩法由哪几块组成

| 文件 | 层 | 是什么 |
|---|---|---|
| `client/assets/scripts/core/dig/level.ts` | 纯逻辑 | 关卡文件的格式 `LevelFile`、读成 `DigLevel`（`parse`）、数据检查（`problems`）、`kindOf` |
| `client/assets/scripts/core/dig/rules.ts` | 纯逻辑 | 局面 `GameState`（哪颗豆能搬 `diggable()`）、点击 `tap()`、技能 `useSlot()` / `useShunt()` / `useMagnet()`、提示 `hint()`、复活 `revive()`，返回事件列表 |
| `client/assets/scripts/game/board.ts` | 界面 | 像素画：一格一颗带厚度的小方块，密排；被搬走时缩掉 |
| `client/assets/scripts/game/station.ts` | 界面 | 上场位（5 个 + 「＋」）、排队区、小队方块 |
| `client/assets/scripts/game/crew.ts` | 界面 | 小人：什么时候出发、走哪条路（过桥 → 绕到画边 → 走进去 → 抱着豆回火车）、同屏上限 |
| `client/assets/scripts/game/train.ts` | 界面 | 铁轨和火车：车厢里码小方块，装满开走、下一列进站 |

| `client/assets/scripts/game/flow.ts` | 界面 | 局内流程（底座）。标了「玩法」的几处：`hasEffect` / `useSkill` 的技能效果、`LOSE_KEY` / `REVIVE_KEY` 失败原因、`endRun` 的任务计数、`checkTutorial` 什么时候教新技能 |
| `client/assets/scripts/game/labHooks.ts` | 界面 | 难度调试页的整体三档：上场位加减几个 |
| `client/assets/scripts/services/config.ts` | 服务 | `loadLevel()` 读 `config/levels/level_XXXX.json`、`kindOf()` |
| `client/assets/resources/config/levels.json` | 配置 | 关卡总表：总数、难关间隔、上场位数、火车大小、机关首发关 |
| `client/assets/resources/config/levels/level_XXXX.json` | 配置 | 一关一个文件（生成的，不手改） |
| `client/tools/level/import.ts`、`pictures/*.json` | 工具 | 像素画图片 → 格子图（认格子、去背景、对齐到拼豆色板）；图库 |
| `client/tools/level/specs.ts` | 工具 | 每一关用哪幅画、排队区几列、一队的数字多大、要多难 |
| `client/tools/level/build.ts`、`solve.ts` | 工具 | 关卡生成；求解器和两个机器人量具 |
| `client/tools/level/verify.ts` | 工具 | `./run.sh level-verify`（CI 跑） |
| `client/tools/art/proto.mjs` | 工具 | 代码画的图：拼豆和它的高光片、小队方块、铁轨、技能图标 |
| `client/tests/dig.test.ts` | 测试 | 规则、技能、胜负边界、每一关的文件和参考解 |

## 2. 接口

**纯逻辑**（`core/`，不 import `cc`，不碰时间、存储、`Math.random`）：

```ts
parse(file: LevelFile, 降档 = 0): DigLevel          // 读一关；降档用文件里的 ease 变体
kindOf(cfg, 关卡号): 'normal' | 'hard' | 'boss'

// 局面：就地修改，返回这一步产生的事件；界面只按事件播动画，不自己推导规则
class GameState { status; loseReason; revived; slotAdded; clone(); diggable(); freeSlot(); canTap(); hasHidden(); ... }
tap(s, 排队区第几列): GameEvent[]        // 最前面的方块上场；点不动返回 []
useShunt(s, 列, 第几个): GameEvent[]     // 技能「调队」
useSlot(s): GameEvent[]                  // 技能「加位」
useMagnet(s): GameEvent[]                // 技能「磁铁」（每关 1 次）
tick(s, dt): GameEvent[]                 // 限时
hint(s): 该点哪条线 | -1                  // 闲置提示、机器人代打共用
revive(s, 加时秒数): GameEvent[]         // 复活：场上的小队吸走自己颜色的豆
```

事件见 `docs/01` 第 1.4 节。

**界面接口**（`gameView.ts` 给 `flow.ts` 用的）：`s`、`lv`、`arg`、`combo`、`used`、`moved`、`ended`、`paused`、`items`、`departed`、`quiet`、`isPicking`、`doTap()`、`act(fn)`、`resync()`、`startPick()` / `endPick()`、`refreshSkills()`、`showIntro()`、`startTutorial()`。

**连击**：这款游戏不做（`docs/01` 第 1.5 节），`hitCombo()` 没有地方调；连击的满屏表现是底座的，代码留着。

## 3. 改玩法、加机关的步骤

1. 先改 `docs/01` 第 1 节（规则、事件、技能、失败原因），大改先讲给用户、确认后动手（CLAUDE.md）。
2. 改 `core/dig/` 和 `client/tests/dig.test.ts`：每条规则、每个技能、胜负边界各一两个用例。`./run.sh test` 通过。
3. 关卡文件的格式有变就改 `LevelFile`、`parse`、`problems`、`tools/level/build.ts`，重新生成全部关卡。
4. 改 `game/board.ts`、`station.ts`、`crew.ts`、`train.ts`，和 `gameView.ts`、`flow.ts` 里标了「玩法」的地方。技能有变还要改 `economy.json` 的 `skills.order`、`toolPrice`、`toolStart`、`features.skill_<id>`，技能图标 `icon/skill_<id>.png`，文案 `H_SKILL_<ID>`，音效（`services/audio.ts` 的 `MAP`）。
5. 失败原因文案 `UI_LOSE_*`、复活效果 `REVIVE_*`、开局说明 `TIP_*`（挂在 `game_ui.json` 的 `tips`）、加载页小提示 `BOOT_TIP_*`。
6. `./run.sh check`、`./run.sh level-verify` 通过，再去 Mac 上 `./run.sh` 试玩、`./run.sh auto` 让机器人代打一遍。

## 4. 关卡

- **进包的关卡必须可解**（CLAUDE.md）：每关带一条参考解（按这个顺序点方块一定能过，不用技能），`./run.sh level-verify` 逐关照着打一遍。
- **来源：离线生成的关卡文件**，一关一个 `config/levels/level_XXXX.json`。微信版放到网上下载（`docs/04` 第 7 节）。
- **先有画，再配队伍**。难度有一半在画里（第 6.1 节），所以顺序不能反过来。流程：

| 步 | 做什么 | 谁 |
|---|---|---|
| 1 | 写出图需求：题材、格数（10 到 32）、最多 9 种颜色、每个像素是一个纯色方块、要哪种结构（第 6.1 节：并排 / 轮廓线 / 一圈套一圈） | AI |
| 2 | 按需求画像素画，存 `art/raw/`。题材和画法自己定，不照任何现有游戏的图（CLAUDE.md 硬性约束 1） | Codex |
| 3 | `npx tsx client/tools/level/import.ts <图片> <名字> <中文名> [颜色数]`：先认出图里实际的格子（Codex 画的格数和要的常常不一样）→ 每格取中间一块的颜色，品红背景算空格子 → 相近的颜色并成一种，零星杂色并进最接近的 → 每种颜色换成拼豆色板里最接近的（整个游戏的豆只用这一套鲜艳的颜色，在 `import.ts` 的 `PALETTE`）；写成 `client/tools/level/pictures/<名字>.json`，另出一张「原图 / 转出来的」对比图 | AI |
| 4 | 量这幅画（第 6.1 节的四个数），决定它适合放在哪一段、当普通关还是难关 | AI（工具） |
| 5 | 看对比图：图案好不好看、转得对不对 | 用户 |
| 6 | 配队伍：模拟从外往里的搬豆顺序 → 沿着它按颜色切成一队一队（这就是参考解）→ 分到排队区的几列里 → 朝目标难度一步步打乱、合并、拆分、加机关，每一步都用求解器确认有解、用机器人量过关率 | AI（`client/tools/level/build.ts`） |

- **Codex 不守格数**：要 16 格的图，画出来的「一个像素」大小不一定，实际常常是二三十格。所以画多大以转出来的为准，出图需求里的格数只是大概；要小画就让它画得更简单。
- **关卡文件里有什么**：画的宽高和格子（`w`、`h`、`layers`，叠层画有两层；做了云朵以后加 `clouds`：每朵云盖哪些格子、什么颜色）、颜色表（`palette`）、排队区每一列的方块（`c` 颜色、`n` 数字，可选 `link` 和谁连体、`lock` 哪把锁、`mystery` 问号）、钥匙挂在哪一格（`keys`）、上场位数、火车大小、类型（`kind`）、用到的机关、参考解、降档变体（只换队伍，画不变）、量出来的难度数据（`meta`）。
- **降档变体**：第 1 档把队伍的顺序往参考解靠一半；第 2 档完全按参考解的顺序轮流分到各列，并把大队拆小。

## 5. 关卡节奏与难度曲线（底座的原则，照这个排）

这一节是底座排关卡的默认原则。这款游戏的排布表在 `docs/01` 第 2 节，对照这里检查；要偏离先讲理由、用户确认。

### 5.1 取向

- **玩法早出完，难度早到位，之后持平**：多数玩家打不到第 80 关，排在那里的玩法等于没人看到。所有玩法在前 20 关出完，第 21–40 关组合练习、难度爬上去，第 41 关起难度持平，不用几百关慢慢往下压。
- **后面的新鲜感靠收集，不靠一直加难**：每一章出新的画，玩家为了收集往下打；难度一直涨只会把人劝退。
- **一关长一点没关系，不为了缩短时长砍内容**：一关三分钟左右可以接受；嫌一关拖，先看是不是难度太高、反复输，而不是减少关卡里的东西。

### 5.2 默认排法

| 项 | 默认 |
|---|---|
| 关卡数 | 生成多少都行，但**按玩家进度分批生成**（5.5），先做前 50 关 |
| 教学 | 前 3 关怎么点都能过，一关只教一件事 |
| 第一次会输 | 第 4–5 关起开始有真实的失败 |
| 玩法出现 | **前 20 关出完全部玩法**：一关最多一样新东西，新玩法不在难关首发；首发关是教学关（比同位置容易一截），下一关马上再练一次 |
| 难度 | 第 1 章（1–20 关）教，第 2 章（21–40 关）把玩法组合起来练、难度爬上去，**第 41 关起持平**（普通关、难关、超难关各一个固定的目标）；最后一次加难也放在第 41 关 |
| 单局时长 | 三分钟以内都可以；用 `pace` 设一个上限防止失控，不靠砍内容缩短 |
| 难关 | 每 5 关一个难关；超难关每 20 关一个，第一个在第 20 关 |
| 放松 | 难关、超难关之后的那一关明显轻松（目标放宽） |
| 先教后用 | 技能解锁关强制教学并送一个；之后一两关内安排一关正好用得上它的难点（第 4 关教加位、第 5 关是第一个难关） |
| 功能开放 | 同一关不开两样东西；技能、主页功能、局内新玩法错开 |

### 5.3 「前面太简单」先查这几样

难度感受不到时，多半不是关卡本身的问题：

- **免费道具**：前几关技能全免费（`economy.json` 的 `skills.freeAllUntil`、`toolMaxFree`），玩家堵了就用，规定路线的难度直接没了。免费期越长，前面越像「无脑过」。
- **试玩模式**：`./run.sh` 默认资源加满。验收难度用 `./run.sh real`，并且不用技能打。
- **尺子和真人不一样**：机器人量出来的是「随手点 / 稳妥点 / 想清楚」三种人的过关率；认真玩、会看后排的人接近「想清楚」那一档，对他来说比尺子说的容易得多。定目标时要想清楚这一关是给哪种人设计的。

### 5.4 怎么落到配置里

`config/levels.json`：`total`（做好了几关）、`hardEvery` 5、`bossEvery` 20、`slots` 5、`train`（一列几节、一节几颗）、`mechanicFrom`（机关 → 第几关首发：连体 6、问号 11、锁 13、叠层 17；云朵确认后把叠层换成云朵）、`pace`（时长上限：估算秒数 = 豆数 × `beadSec` + 点击次数 × `tapSec`；普通关 150、难关和超难关 180）。每一关要多难写在 `client/tools/level/specs.ts`，生成器照着配。`./run.sh level-verify` 会列出超时长的关、首发关之前用了机关的关。

### 5.5 关卡按玩家进度分批生成

不一次把几百关都生成完。改了难度或玩法以后，只重新生成玩家眼下打得到的那一段（先做前 50 关），后面的关保持原样或者先不做；等有玩家快打到了再往后生成下一批。汇报里写清楚哪一段是新规则生成的、哪一段还是旧的。

### 5.6 参考（个人分析文章，不是官方数据，只当参考）

关于「先教道具、下一关就用得上」「难关之后给放松」的来源。文章里关于单局长短的结论我们没有采用（见 5.1 第三条）。

- Pixel Flow：作者自己按第 1–20 关各打 10 遍，第 18 关教了强力道具、送一个，第 19 关平均用时从 26 秒跳到 165 秒，是唯一稳定会输的一关；作者也说不确定是不是有意设计。[Gamigion：Interesting Tricks in Pixel Flow](https://www.gamigion.com/interesting-tricks-in-pixel-flow/)
- 同玩法的后来者：作者一个人打到第 100 关，平均每关比 Pixel Flow 长约 12 秒；后来者从第 41 关左右起几乎关关超过 1 分钟；Pixel Flow 中后期仍不断插入 40 秒以内的短关，Very Hard 之后给明显的放松。[Gamigion：Why did the latecomers fail](https://www.gamigion.com/why-did-the-latecomers-built-on-essentially-the-same-core-play-fail-to-produce-the-same-result/)

## 6. 难度怎么定义、怎么量

### 6.1 难度是什么

一关的难度 = **玩家有多容易叫错队伍、把 5 个上场位都占住**。它由两样东西决定：画，和队伍怎么排。

**画决定「先后顺序有多死」。** 同样的颜色数，画的结构不同，难度差很多。导入一幅画以后工具先量四个数：

| 量什么 | 怎么量 | 说明什么 |
|---|---|---|
| 同时露出几种颜色 | 模拟从外往里一圈圈搬，每一步数一下露在外面的有几种颜色，取平均 | 越少，玩家每一步能选的越少、越容易叫错 |
| 颜色的先后约束 | 有多少对「不先搬掉 A 就搬不到 B」 | 越多，顺序越死 |
| 一种颜色分成几片 | 同一种颜色不相连的区域数 | 越碎，这种颜色要分越多次上场，每次都可能叫早 |
| 最里面有多深 | 最里面那颗豆，要先搬掉外面几圈才露出来 | 越深，一局越长、中途出错的机会越多 |

常见的三种结构，从松到紧：

| 结构 | 样子 | 难度 |
|---|---|---|
| 并排 | 几块颜色左右、上下挨着，都挨着画的外边 | 松：很多颜色同时露着，怎么叫都有活干。教学关用 |
| 轮廓线 | 一圈背景色包着一个有深色描边的图案，描边里面是填色 | 中到紧：背景先走，描边是「门」，描边没搬完里面全都搬不到。多数关用这种 |
| 一圈套一圈 | 颜色一层包一层，每一层都把里面完全围住 | 最紧：顺序几乎是唯一的。难关、超难关用 |

铺满的方形画比轮廓形的画紧（外边只有背景一种颜色露着）。

**队伍怎么排决定「玩家看到的选择有多坑」。** 旋钮按影响从大到小：

1. **错位度**：方块排队的先后，和画从外往里搬得到的先后错开多少。错得越多，最前面越常是「现在没豆可搬」的颜色。
2. **数字比露出来的多**：一队 40，眼下只露出 12 颗，它就要占着位子等很久。大队伍放在它的颜色只露出一点的时候，是最主要的坑。
3. **排队区几列**：列越多，玩家能选的越多、越松；2 列最紧。
4. **颜色数**：颜色越多，5 个位子越不够分。
5. **机关**：连体块一次占 2 个位子、而且两块都搬完才走；问号块看不到后面是什么；锁把一整列挡住，直到钥匙那颗豆被搬走。
6. **画的大小**：豆越多，一局越长。受单局时长限制，不能一直加。

上场位固定 5 个，是玩家心里的尺子，不拿它调难度。

### 6.2 怎么量

只用屏幕上看得到的信息（问号块对机器人也是问号），每关各跑几百局，结果记进关卡文件的 `meta`：

| 量具 | 是什么 | 说明什么 |
|---|---|---|
| 随手点 | 随机点一个点得动的方块 | 不动脑能不能过 |
| 稳妥点 | 只叫「现在有豆可搬」的颜色（有几个就叫能搬得最多的）；没有这样的才随机点 | 按常识玩能不能过。也是提示、机器人代打用的 |
| 想清楚 | 稳妥点的基础上，往后看几步：看排队区后面排着什么、这一队搬完会露出什么颜色 | 认真玩的人能不能过。守住公平：这一档过不了的关不进包 |
| 最少占位 | 求解器算：所有解法里，最紧的时刻最少要占几个位子 | 2–3 宽松，5 是一步不能错 |

求解器只用来保证有解和算「最少占位」，不拿它当难度——求解器说有解，不等于玩家过得去。

### 6.3 各类关卡的目标

| 关 | 随手点 | 稳妥点 | 想清楚 |
|---|---|---|---|
| 教学关（第 1–3 关、技能和机关的首发关） | 100% | 100% | 100% |
| 放松关（难关、超难关后面一关） | 不低于 70% | 100% | 100% |
| 普通关，第 4–20 关 | 85% 降到 60% | 100% | 100% |
| 普通关，第 21–40 关 | 55% 降到 35% | 不低于 90% | 100% |
| 普通关，第 41 关起（持平） | 30%–40% | 80%–90% | 100% |
| 难关，第 5 关 | 30%–45% | 75%–90% | 100% |
| 难关，第 10 关 | 20%–30% | 65%–80% | 100% |
| 难关，第 15 关起（持平） | 10%–20% | 50%–70% | 不低于 95% |
| 超难关（第 20、40、60… 关） | 低于 10% | 30%–50% | 不低于 90% |

好的难关是「想清楚能过、随手点会输」，不是「怎么点都看运气」。

### 6.4 各段的画和队伍

| 段 | 关 | 画 | 豆数 | 颜色 | 结构 | 队伍数 | 一队的数字 | 排队区 |
|---|---|---|---|---|---|---|---|---|
| 教学 | 1–3 | 10×10 到 14×14 | 40–120 | 2–4 | 并排 | 3–6 | 8–30 | 2 列 |
| 第 1 章 | 4–20 | 16×16 到 24×24 | 150–400 | 4–6 | 并排、轮廓线 | 8–16 | 5–40 | 3 列 |
| 第 2 章 | 21–40 | 22×22 到 28×28 | 300–600 | 5–8 | 轮廓线为主 | 14–24 | 3–60 | 3–4 列 |
| 持平 | 41 起 | 26×26 到 32×32 | 450–800 | 6–9 | 轮廓线、一圈套一圈 | 18–30 | 3–80 | 4 列 |

单局时长按「豆数 × 0.2 秒 + 点击次数 × 1.2 秒」估（同屏几支小队一起搬，一秒搬 5 颗左右），普通关不超过 150 秒，难关、超难关不超过 180 秒。超了先看是不是难度太高，其次把小人走快一点，最后才把画改小。

### 6.5 连输降档

同一关连输 `easeAfterFails` 次，换成关卡文件里降档变体的下一档（第 4 节）；画不变。

## 7. 以后怎么加关卡和机关

- **加关卡就是加文件**：新的 `level_XXXX.json` 加进去，改 `levels.json` 的 `total`。难度照第 6.3、6.4 节「持平」一档，用同一套量具量，不用重新设计曲线。
- **按关卡包更新**：一包 20 关（一章），一个新题材的一批画；可以带 1 个新机关（`docs/01` 第 1.7 节末尾列了备选）。
- **机关各自独立**：每个机关是规则里单独的一块（能不能搬、能不能点、搬走时触发什么），加新机关不改已有的；关卡文件用 `mechanics` 声明用了哪些。
- **首发关写在配置里**：`levels.json` 的 `mechanicFrom`。想把某个机关提前或推后，改这里和对应的关卡文件；`level-verify` 检查「首发关之前没有关卡用到它」。
- **打完现有关卡**：照底座在后一半关卡里循环（`docs/01` 第 4.12 节），直到新关卡包上线。
- **怎么发**：微信版关卡文件在网上，更新不用重新提审；iOS、Android 跟着新版本发。
- **看数据再调**：上线后按每关的通过率、流失调降档变体和个别关卡文件，不动规则。
