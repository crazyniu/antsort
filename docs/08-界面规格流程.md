# 08 界面规格流程

目的：避免「做完才发现不好看、不好用」。底座已有的页面（`docs/09` 第 6–9 节）不用再写规格；**新游戏新加的界面**（新玩法的场地、新的弹窗、新的页面）在写代码前先有一份规格，写完后按清单审查。

## 1. 流程（每个界面都走）

1. **写规格**：`docs/ux/<界面名>.md`，按第 2 节模板。Claude 先对照 3 个以上同类游戏的做法写出「参考结论」（只取结构与原则，不取画面）。
2. **用户确认规格**：确认前不写界面代码。
3. **做外壳**：假数据、可点击、带动效，遵守 `docs/09` 的设计系统，只用 `ui/kit.ts` 的部件。
4. **审查**：Claude 在 Mac 上截图，逐条过第 3 节清单，结果写进 PR 说明；用户验收。
5. **接逻辑**：验收后才接 `core/` 逻辑。

## 2. 规格模板

- **玩家目标**：玩家进入这个界面，最想做的一件事（只能一件）。
- **主次层级**：主行动 1 个；次行动不超过 3 个；其余是信息。写明每项的相对大小和位置。
- **布局**：750×1334 设计稿，标出安全区（顶部刘海、底部手势条）、拇指热区（下半屏）。
- **状态**：默认、未解锁、有红点、加载中、出错、空。
- **动效**：进场、常驻、点击反馈各一句，且可跳过。
- **文案**：键名与各语言。每种语言按同类休闲手游里的叫法写，不逐字互译（例：抽奖英文写 Lucky Box、技能英文写 booster、失败写 Level Failed / Out of moves）；能短就短，按钮只写动作或结果；界面上叫什么、局里就叫什么，一个词不混用（文档里的设计用词「技能」「暂存槽」，玩家看到的是「道具」「槽位」）。
- **参考结论**：同类游戏怎么做、我们取什么、不取什么。
- **验收点**：3–5 条可检查的话。

## 3. 审查清单

1. 3 秒内能看出主行动是什么？
2. 主按钮在拇指热区、够大（高度不小于 96）、全屏只有一个视觉最强的按钮？
3. 同级元素尺寸、间距、对齐一致（8 的倍数、同一中线）？
4. 文字最小 24，对比清楚，不被背景吃掉？中文无斜体、无旋转？
5. 所有可点区域不小于 88×88？
6. 顶部、底部避开安全区？微信胶囊按钮下面才能放东西？16:9 短屏、4:3 宽屏也排得下？（`docs/09` 第 1 节）
7. 各状态都做了？未解锁的有明确提示？
8. 动效有节制：常驻动效不超过 2 处，不抢主按钮？
9. 与其它界面风格一致，只用 `ui/kit.ts` 的部件？
10. 没有硬编码文案、魔法数字？
